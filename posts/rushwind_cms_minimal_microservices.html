RushWind CMS — 最小微服务实例：微服务架构的最小完备集

本文回答一个问题：微服务架构最少要保留哪几样东西才仍然成立？注册中心、网关、消息总线、分布式事务、服务网格这些"标配"，真的是必需品吗？RushWind CMS 用三个进程、一种内部协议、零控制面中间件，把这套账算到了最小。

RushWind CMS 是一套 Rust 全栈 Headless 内容平台，后端是三个进程：core-service 独占数据库、admin-api 与 app-api 两道 BFF 对外。姊妹篇《三服务拓扑》把每道接缝的机制拆开过——本文换一个视角算总账：把微服务拆到不能再拆还成立的时候，剩下的那几样东西是什么；传统技术栈里的每一件中间件，又是凭什么被省掉的。

一、微服务的最小完备集

微服务的本质不是中间件堆栈，是三件裁不掉的事：

  • 进程边界——每个服务是独立的部署单元，有自己的故障域与发布节奏；
  • 数据独占——每份数据只有一个主人，别的服务想用，走它的接口；
  • 契约先行——服务间通信的形状有一处权威定义，改契约就是改接口。

这三件事之下，微服务成立。其余的一切——注册发现、API 网关、消息总线、分布式事务框架、服务网格——都是这三件事在规模变大之后的补丁。补丁本身没有错，问题在于它们常被当成入场券：似乎不配上整套控制面，就不配叫微服务。

RushWind CMS 给出的反例是一张表——传统栈的每个部件，在这个项目里的存在形态：

传统微服务栈本项目的形态
注册中心 / 服务发现一条配置地址 + 一条共享连接
API 网关产品BFF 就是网关（admin/app 两张脸按消费端切）
消息总线进程内 SSE Hub + gRPC metadata 带收件人列表
分布式事务框架不存在——事务边界与进程边界重合
服务网格无——进程边界 + 一种协议 + 显式 metadata
配置中心嵌入式默认配置 + 环境变量覆盖
可观测栈（tracing/log）缺席——错误信封 + E2E 充当裁判

注意这不是"偷工减料"的清单：每一行的替代物都真实工作，且各自有一个能写下来的结构性理由。下面逐行展开。

二、全部拓扑就是三个进程

整个后端是一个 Cargo workspace，编出三个二进制、四个端口，没有第四个进程——没有 sidecar，没有守护代理，没有编排依赖：

backend/
├── api/          契约层：proto 快照（MANIFEST 校验门）+ buf 工作区
├── crates/       proto（契约 crate）/ store（数据层）/ auth（鉴权门）
├── services/
│   ├── core-service/   领域层（gRPC :6602，独占 PG/Redis，不对外暴露）
│   ├── admin-api/      管理 BFF（REST :6600 + SSE :6601）
│   └── app-api/        前台 BFF（REST :6700 + SSE :6701）
└── scripts/      生成器（gen-proxies / gen-entities）+ e2e-test.sh

仓库根 AGENTS.md 把启动顺序写成三行：core-service 先起（空库自动引导 schema + 种子 + 演示数据），admin-api、app-api 随后。这个顺序由人手保证，不由就绪探针保证——三个进程的依赖关系简单到一条直线，为它引入编排系统反而是把简单问题复杂化。

每个二进制的 main 都短到一屏：读配置、连依赖、起服务器。以 core-service 为例，它起的是一个 tonic gRPC 服务器，挂上全部领域服务：

进程边界在这里就是部署边界：cargo run -p core-service 是领域层，cargo run -p admin-api 是管理面。每个二进制都是自包含的原生可执行文件——不带运行时、不带容器镜像层，「一个进程一个服务」的部署语义被 Rust 的编译模型直接兑现。三个进程可以各自重启、各自替换——这是「微服务」三个字里微的全部含义，也是它最便宜的部分。

三、服务发现的最小替代：一条地址、一条共享连接

BFF 怎么找到 core？看它的状态结构：

// backend/services/admin-api/src/state.rs
pub struct AppState {
    pub cfg: Config,
    pub redis: ConnectionManager,
    /// The verification engine the auth gate rides (shared secret).
    pub authenticator: Arc<dyn rushwind_authn::Authenticator>,
    /// The gRPC channel to the core domain service — the shared dial
    /// every per-service client clones.
    pub core_channel: tonic::transport::Channel,
    /// The authentication face (the login/logout/validate client).
    pub core: AuthenticationServiceClient<tonic::transport::Channel>,
    /// The SSE notification hub (`/events` subscribers).
    pub hub: crate::server::sse::Hub,
}

建立连接的代码只有一次拨号：

let channel = tonic::transport::Endpoint::from_shared(cfg.core_addr.clone())
    .map_err(|e| format!("core endpoint: {e}"))?
    .connect()
    .await
    .map_err(|e| format!("core connect {}: {e}", cfg.core_addr))?;

没有注册中心，没有健康检查轮询，没有客户端负载均衡——core_addr 是一个配置项，启动时拨一次，之后 BFF 里每一个领域客户端都克隆同一条 Channel（tonic 的 Channel 是多路复用的，一条连接承载全部并发调用；app-api 侧完全同构）。

这个"简陋"是算过账的。服务发现解决的问题是实例集合漂移：服务会扩缩容、会滚动发布、地址集合随时间变化。而当拓扑钉死为「一个 core、两个 BFF」时，集合不漂移，一条地址就是全部事实。扩张点也在结构里预留好了：Channel 是 Clone 的，哪天 core 要水平扩容，把 Endpoint::from_shared 换成带负载均衡的 Endpoint 工厂即可，BFF 里 72 + 13 个代理调用点一行不改——因为它们只依赖"一条能用的 Channel"这个抽象，不依赖它怎么来的。

四、进程间只有一种协议，错误是契约的一部分

三个进程之间只有一种通信方式：gRPC（tonic）。对浏览器与小程序只有一种应答方式：REST + SSE。没有第三种进程间通道——没有消息队列，没有事件总线，没有 RPC/HTTP 双栈并存。

协议只有一种的直接红利是：错误语义只需要翻译一次。 跨进程边界传播的错误有一条固定的链路：领域服务抛 StatusResult → tonic Status → BFF 侧一张显式映射表 → HTTP 错误信封。这张表就住在 services.rs：

// backend/services/admin-api/src/services.rs
/// The tonic Status → the admin BFF's four-field envelope (the
/// error-table anchors the reason when the code maps onto one).
pub fn map_status(e: tonic::Status) -> StatusError {
    let reason: &'static str = match e.code() {
        tonic::Code::InvalidArgument => "BAD_REQUEST",
        tonic::Code::Unauthenticated => "UNAUTHORIZED",
        tonic::Code::PermissionDenied => "FORBIDDEN",
        tonic::Code::NotFound => "NOT_FOUND",
        tonic::Code::AlreadyExists | tonic::Code::Aborted => "CONFLICT",
        _ => "",
    };
    if reason.is_empty() {
        crate::state::internal_error(e.message())
    } else {
        crate::state::status_error(reason, e.message())
    }
}

AGENTS.md 的铁律 5 与之配套：不吞错——错误必须映射传播，不允许静默丢弃。这条规则在多协议栈里最难执行（每条链路一种错误形状，吞错处藏不住），在单协议栈里却几乎免费：所有跨界错误都流经同一张表，前端拿到的 reason 信封全栈同形。

异步的那部分也不需要总线。领域服务要推送事件时，收件人列表搭 gRPC 响应的 metadata 回给 BFF，由 BFF 的进程内 Hub 按 uid 扇出到 SSE 流——机制细节在姊妹篇第五节，这里只记架构结论："服务间解耦推送"在这套规模下退化为"一次函数边界清晰的双进程接力"，总线的解耦收益（生产者消费者互不知晓、各自伸缩）在这个拓扑里无从兑现，成本却是真实的。

五、数据只有一份主人，于是分布式事务不存在

微服务实践里最重的一类复杂度是跨服务数据一致性：saga、补偿事务、最终一致、对账job。这一整类问题在 RushWind CMS 里结构性不存在，因为铁律 2 把数据所有权钉死在单点：

BFF 不碰数据库：admin-api / app-api 只做协议转换与转发；数据访问只发生在 core-service。

这不是规范建议，是结构事实——两个 BFF 的代码里不存在数据库连接。于是一个关键等式成立：事务边界 = 进程边界。一次写操作无论跨多少张表、多少个领域模块，只要发生在 core-service 进程内，就是一个普通 PostgreSQL 事务——原子性由数据库保证，不需要任何补偿框架。admin 改一篇帖子连着写审计日志？同一个事务。角色删除顺带摘除子角色绑定？还是同一个事务。分布式事务的整套词汇（协调者、投票、悬挂补偿）在这里没有可以附着的位置。

缓存与存储按域分租，同样每份数据单主人：会话键族（gwc:at/rt/bl）只有 core 读写；验证码（cms:captcha:*）是 BFF 的本地小状态；对象存储只有 core 的文件面触碰。Redis 虽然两个进程都连，但键空间互不越界——所有权按键族划分，而不是按机器划分。schema 演进同理只有一个主人：黄金 DDL 管线住在 store crate、由 core-service 启动序列执行，BFF 对表结构一无所知。

六、身份与租户随行：metadata 是最小的上下文载体

跨进程调用需要随行的不是只有参数，还有"谁在调用"。这套系统里没有 trace context，但身份与租户的 context 是必选的，它的载体选了最薄的一种：gRPC metadata。

BFF 侧把验签后的 claims 注入两个 header，这是全仓唯一的注入点：

// backend/services/admin-api/src/services.rs
/// Wraps the outbound message with the operator metadata (uid/tid from
/// the verified claims) — the core service reads it where the proto
/// carries no user field (the interaction ledger writes).
pub fn with_operator<T>(
    ctx: &rushwind_http_binding::ctx::RequestContext,
    msg: T,
) -> tonic::Request<T> {
    let mut req = tonic::Request::new(msg);
    if let Some(claims) = &ctx.claims {
        if let Some(uid) = claims.get("uid").and_then(|v| v.as_u64()) {
            if let Ok(v) = uid.to_string().parse() {
                req.metadata_mut().insert("x-user-id", v);
            }
        }
        if let Some(tid) = claims.get("tid").and_then(|v| v.as_u64()) {
            if let Ok(v) = tid.to_string().parse() {
                req.metadata_mut().insert("x-tenant-id", v);
            }
        }
    }
    req
}

core 侧对称：一个文件（context.rs）收拢全部提取逻辑， faces 之间不再各带私货：

// backend/services/core-service/src/service/context.rs
/// The operator user id off the gRPC metadata the BFF forwards
/// (`x-user-id` from the verified claims) — required.
pub fn operator_of<T>(request: &tonic::Request<T>) -> Result<i64, tonic::Status> {
    request
        .metadata()
        .get("x-user-id")
        .and_then(|v| v.to_str().ok())
        .and_then(|v| v.parse::<i64>().ok())
        .filter(|v| *v > 0)
        .ok_or_else(|| tonic::Status::unauthenticated("user identity required"))
}

/// The trusted inner tenant stamp: the anonymous chain's explicit
/// `x-md-global-tenant-id` (the reference's metadata channel) wins,
/// else the operator bag's `x-tenant-id`.
pub fn request_tenant_of<T>(request: &tonic::Request<T>) -> i64 {
    for name in ["x-md-global-tenant-id", "x-tenant-id"] {
        if let Some(v) = request.metadata().get(name).and_then(|v| v.to_str().ok()) {
            if let Ok(n) = v.parse::<i64>() {
                if n >= 0 {
                    return n;
                }
            }
        }
    }
    0
}

注意这套传播模型的信任前提：core 直接把 metadata 里的 x-user-id 当作授权凭据，自己不重复验签——这成立，是因为 :6602 端口不对外暴露，能拨到 core 的只有先过了 BFF 鉴权门（本地验签 + 远程 ValidateToken 双段）的调用方。信任边界钉在网络层而不是代码层：公网流量到不了 metadata 所在的那条连接。会话裁决的 verdict 只有一个来源（core），租户的裁决键也只有一个提取处——横切上下文的最小实现不是某个 context 框架，是"一个注入函数 + 一个提取函数 + 一条不对外暴露的内网端口"。

七、契约是唯一的接口权威

三个进程对外的全部接口，来自同一棵 proto 树。当前的规模：209 个 proto 文件，982 条 RPC 声明，169 个 service 块；core-service 实际挂载其中 43 个领域服务，其余的声明在契约里、实现在路上——而缺席者不是静默 404，registry 的行为写在文件头：

// backend/services/core-service/src/server/mod.rs
//! The domain gRPC service implementations. A service absent from the
//! served list (or a method left to its generated default) answers
//! Unimplemented — the reference's servers register every module the
//! same way and land their logic module by module.

契约先行的完整含义在这段注释里：契约的边界可以领先于实现的边界，但两者的差距必须有明确的应答（Unimplemented），而不是把"还没写"伪装成"不存在"。同一棵契约树长出三样东西——共用消息类型、core 的 tonic 面、两张 BFF 的 REST 面——投影机制在姊妹篇第二节拆过，不赘述。

契约权威的执行面还有一个细则，钉在 AGENTS.md 铁律 3：int64 字段在 protojson 面上一律字符串化——构造或断言 JSON 时写 "expires_in":"900" 而非 900。这条规则落地那一次，是 88 个 proto、946 处字段类型的整树变更，buf breaking 先行记录再接受，五个前端快照随清单同步重钉——契约动一处，gRPC 与两张 REST 面、五个前端同时变。接口权威收归契约的代价（变更必须整树走门）与收益（不存在"REST 改了 gRPC 忘了"）在同一次演练里都兑现了。

消费这棵树的终端：管理后台与四套 C 端门户（React / Vue / Taro / Flutter）消费同一个后端栈——契约有几个消费者，权威就有几分意义：

八、可观测的最小形态：没有 tracing，裁判是 E2E

这是"省掉的清单"里最激进的一行，如实记录：整个 workspace 没有一处 tracing / log 依赖，服务代码里没有一行日志调用——进程内的执行过程是暗的。

暗的执行过程要能活下来，必须有别的裁决器。这套架构选了两件：

  • 结构化错误信封。上一节的 map_status 链条保证每个失败都有 reason 可断言——"错"不是日志里的一行字，是响应里的一个字段，测试可以直接对它下手；
  • E2E 对接缝的覆盖。backend/scripts/e2e-test.sh 在三服务栈全起后跑 120 个断言点、11 个覆盖节：验证码与登录链、门控路由（401 信封形状）、13 个模块的种子读、CRUD、刷新轮换与登出全吊销、app 公开面、权限与审计、聚合面、multipart 文件（MinIO）、SSE 与 CORS、边界面（Range 206/416、草稿不可见、待审评论不可见）。

断言的层级跟着架构走：会话类断言打 core 的语义，门控类断言打 BFF 的门，领域规则类断言打 core 的表——三服务每一道接缝都有一节断言对着它。这是最小实例的观测观：架构由测试裁决，而不是由仪表盘裁决。它当然有边界——一旦进程多了、调用链深了，"哪一跳慢了"无从回答——所以可观测栈是这张缺席清单里第一件该加回来的东西，而扩张点已经天然存在：错误通道是结构化的，日志与追踪可以沿着 map_status 与 with_operator 这两处单点接进去，不必新开横切面。

九、缺席清单的账本

把散在各节的理由收拢成一张账——每件被省掉的中间件，对应一个结构性替代物与一条成立的理由：

缺席的部件结构性替代物成立的理由
注册中心 / 服务发现一条 core_addr + 共享 Channel拓扑钉死为 1 core + 2 BFF，实例集合不漂移
API 网关产品BFF 双脸（生成代理表 + 手写行为面）差异化语义按消费端切，BFF 本来就是网关的职责
消息总线gRPC metadata 带收件人 + BFF 内 Hub 扇出事件消费方固定且单一，解耦收益无从兑现
分布式事务框架单主人数据，事务 = 进程内 DB 事务数据所有权单点，跨库一致性这一类问题不存在
服务网格进程边界 + 单协议 + 显式 metadatamTLS/重路由/熔断等网格收益在大拓扑才出现
配置中心嵌入式默认 + env 覆盖配置项个位数，变更频率远低于发版
可观测栈结构化错误信封 + E2E 120 断言调用链深度为 1（BFF→core），暗执行可被断言覆盖

这张表反过来读也成立：每一行都有一个明确的加回条件——core 水平扩容时加发现与均衡，消费方不再固定时加总线，调用链超过一跳时加追踪。最小微服务不是永远不装这些部件，而是每一个部件都等到它的加回条件出现那天再装，且装的时候知道接在哪。

十、机制 × 关键决策 × 失败模式

机制关键决策失败模式（若无此决策）
三进程边界边界 = 部署单元，独立发布与故障域单体一把梭，领域间故障与发布互相牵连
单地址拨号拓扑钉死，一条 core_addr + 共享 Channel被注册中心绑架，最小部署背整套控制面
单一内部协议进程间只有 gRPC，错误映射表显式跨界多协议并存，错误语义每条链路各说各话
数据单主人BFF 无 DB 连接，事务边界 = 进程边界服务互连对方库，跨库一致性需要 saga 补偿
metadata 随行注入/提取各一个函数，全仓单定义处身份与租户散落请求体字段，口径漂移
信任钉在网络层core 不对外暴露，metadata 即凭据core 端口外泄，x-user-id 变伪造入口
契约权威209 文件三投影，缺席服务答 Unimplemented接口定义漂移；半成品接口静默 404
断言裁决错误信封结构化 + 120 断言 11 节无裁判时架构腐化不可见，暗执行无从取证

微服务的成本不在三个进程，在进程之间每一层"为了规模化"的基础设施。RushWind CMS 证明这套完备集可以薄到一张表——而它的真正价值是给出一种自检方法：当你能为每一件省掉的中间件写出替代物与加回条件，你才分得清哪些是微服务的本质、哪些只是它的补丁；写不出理由就上中间件，与写不出理由就手写转发，是同一种懒惰。
