RushWind Shop — 一笔订单的穿越：电商买路径上的每一道闸门

本文回答一个问题：在契约驱动的 Rust 三服务电商里，从「点击立即购买」到「库存台账落一行 ORDER_DEDUCT」，中间到底经过了什么？ 每一层各自守哪条线，错了谁兜底，哪些地方刻意「不假装成功」。不谈愿景，只拆一条走得通的路。

RushWind Shop（风行商城）是一套开源的多语言电商平台：后端 Rust，跑在与 RushWind CMS、RushWind Admin 同一套 RushWind 框架底座上—— Protobuf-first 工作流，admin / app 两个无 DB 的瘦网关加一个 core 核心实现。规模实测：契约树 230 个 proto 文件，core 挂载 89 个域服务（59 个单元测试钉住语义），admin 面 467 条路由，app 面 117 条路由，黄金 DDL 90 张表。

商城域不是空壳：仓库自带一套演示种子——22 个商品（122 个 SKU，中英文翻译齐全）、6 品牌、12 类目、27 笔覆盖全部状态的订单、优惠券 / 促销 / 秒杀 / 评论 / 站内信快照，两条命令灌进库，前台就有完整的一套店。

下面把一笔订单从头走到尾。每一节都是代码里真实存在的机制，不是设计稿。

一、进门：AES 信封、图形验证码与两条会话库

买路径的第一步是登录，而登录链的第一道闸门在传输层。前端把密码装进 AES-128-CBC 信封（key=iv，PKCS7，base64 上路），core 收到后先解密、再验凭据——解不开的报文退回明文试探路径，这样开发期的 curl 也能走通，而生产线上没有裸密码上路。信封解出来的明文对 Argon2id 哈希做验证，哈希落在 sys_users.password，登录链只认这一处。

管理后台的登录还要过图形验证码：core 铸一枚 4 位数字码，存 Redis 会话库、5 分钟 TTL，SVG 以 base64 回给前端渲染；校验时按 captcha id 取回比对，一次性消费。前台（店铺侧）的契约没有验证码面——两个消费端的门禁强度由各自的契约声明决定，不搞一刀切。

这一节还有一个用血换来的细节：client_type 必须随登录上报。前台最初的登录调用漏了这个字段，core 把新铸的 token 存进了 admin 会话库，而 /app/v1/me 拿去 app 会话库校验——每次登录「成功」，下一跳立刻 401，结算页陷入重定向循环。修复只有一行（前台钉 client_type: 1），但暴露的结构性事实值得记住：同一套登录面服务两类端时，会话库的分流依据必须是显式契约字段，而不是隐式调用来源。

二、选规格：SKU 组合匹配与「无组合即单 SKU」

商品详情页的规格区由契约数据驱动：属性的 radiogroup 只渲染本品 SKU 组合里真实出现过的属性——不做这道收口，耳机的页面会冒出尺码 S/M（那是别的商品的属性），全局属性表没有 product_id，每个详情页都能看见全部属性。

选中一组规格，前端拿 sku_id 去查价格行，命中的 SKU 决定三件事：价格卡渲染、加购按钮点亮、购物车行随行携带规格快照（「配色: 星辰银，套餐: 单机装」）。没有组合的商品走单 SKU 短路——详情页直接给价，规格区整体不渲染。

这里有一条值得写进契约注释的教训：列表面的过滤器 query 走 go-crud 风格的 JSON 串，值必须是字符串。前端曾用 JSON.stringify({ productId: 100 }) 上路——JSON 数字值让解析器整体失败，错误被静默吞掉，接口「正常」返回了全表。页面没有报错、没有缺数据，只是规格区多了几个不该出现的属性组，购买按钮默默禁用。修复是前端的一处 String()，但真正的结论是：静默吞错 + 宽松入参的组合，故障会以「功能悄悄变弱」的形态出现，而不是一次显眼的报错。服务端调用点要按契约的方言传参，方言本身也应该在解析失败时喊出来。

三、下单：客户端金额是参考值，服务端才是账本

结算页提交订单时，前台刻意把 totalAmount 填 0。这不是偷懒，是立场：金额的唯一来源是服务端。core 的 Order.Create 在一个数据库事务里完成购物车到订单的全部转换——

  1. 找到用户购物车（缺车 / 空车 → BadRequest）；
  2. 插入订单壳，状态 PENDING_PAYMENT（客户端状态字段一律无视）；
  3. 逐项按 sku_prices 的结算币种定价，无价行 → 整个事务回滚；
  4. 快照每个商品项进 order_items；
  5. 扣 SKU 库存，每项落一行 ORDER_DEDUCT 库存台账；
  6. 清空购物车；
  7. 服务端算出的总额回写订单。

这套次序每一条都对着一个具体的历史漏洞：零总额空订单曾经可以被创造甚至支付——那是一个真实的对账洞；库存扣减曾经不落台账——出了争议无从对账。修复不是打补丁，是把「谁说了算」写进事务结构里：结算币种的价格行缺失就回滚，客户端的数字永远只是显示层。

四、收银台：支付意图与确认分离

结算是两段式的。CreatePaymentIntent 先行：app 面的响应是收银台对话框直接可读的扁平形状（交易号、支付方式、金额、币种，外加 redirect / QR 槽位）——这个形状与领域消息不同，所以生成代理的 pass 轨道类型检查不过，这是一个手写行为（hand）：转发核心、映射形状，并按渠道枚举推导支付形态——微信 native 走二维码，支付宝 / 微信 H5 走跳转，其余落到模拟通道，保住演示路径永远可达。

确认是另一段：模拟通道用时间戳造一个网关流水号去走核心的 confirm 面。交易的迁移守卫在这里表态——对一笔已经 SUCCEEDED 的交易再发确认，得到的不是第二笔成功，而是一次迁移拒绝错误。幂等不是「成功覆盖成功」，是「状态机不给重复成功开门」。

五、状态机：拒绝是正确的业务答案

订单状态机在 PAID 上收到「取消」请求时，回答的不是静默成功也不是 500，而是一次明确的业务拒绝——已支付 → 已取消 不在迁移表里。这听上去是常识，但它依赖一个前提：状态迁移只发生在状态机一处，任何直改字段的旁路都会让守卫变成摆设。Shop 把迁移守卫放在 core 的订单面里，BFF 与前端都只发「意图」，不发「结果」。

顺带一个路由层的真实教训：契约里的动词后缀路由（Kratos 风格 /orders/{id}:cancel）在 axum 的 matchit 下有一类无法挂载——参数段后接冒号动词的形状会被并进 GET 参数路由，405 在动词路由注册之前就发生。修复是把三个参数化动词路由挪到 axum 原生的斜杠子路径（/orders/{id}/cancel），生成的路由表与已提交的 TS 客户端同步再生。其余十二个全静态的冒号路由（/tasks:restart、/tenants:exists）matchit 处理良好，保留原样。教训同样关于「静默 vs 显眼」：405 至少会喊，最怕的是形状兼容但语义漂移。

六、库存：每一笔扣减都有台账行

下单事务里的库存扣减不是改一个数字，是两件事同时发生：sku.stock_qty 落到新值，mall_stock_op_logs 落一行 ORDER_DEDUCT（50 → 47 那一行）。台账是库存的司法记录——争议对账时，总量可以重算，过程可以回放。库存告警规则（阈值触发的 alert 行）与操作日志共用这套结构。

七、会员侧的信任结构：claim 强制注入

买路径之外还有一个容易被忽视的安全细节。前台的「我的等级」面在契约上与核心的管理面同名（GetMyTierInfo），但它的 user_id 不允许来自查询串——proto 注释里写明查询串不能点名任意用户，BFF 的 hand 行为强制用登录 claim 里的身份覆盖入参，再转发核心。匿名可读的会员档位列表则显式标注 auth-free，进免鉴权白名单。

这个模式可以推广成一句话：凡是「我的 XX」语义的面，身份必须来自凭据声明，入参只能是过滤条件。Shop 在用户资料、等级、收藏、消息中心上都是同一个处理。

八、缺席清单的账本

电商模板最容易犯的罪是把每样东西都「接了个壳」。Shop 的选择相反——没接的东西如实报 Unimplemented，写进错误码而不是假装成功：

缺席的部件当前状态加回条件
真实支付网关内置模拟通道（收银台完整走通）商户号与渠道密钥就位，confirm 面换网关回执
EMAIL / SMS / WEBHOOK 通知仅落投递台账SMTP / 短信网关 / 回调端点配置
知识库语义检索降级为关键词匹配嵌入运行时接入（provider 已有 OpenAI 兼容运行时）
OAuth 五个线上换发面本地凭据账面完整，线上面 Unimplemented各 IdP 应用配置
MFA 备份码 / 登录挑战起点TOTP 全链路可用，这两处按参考实现同样缺席参考实现的下一轮范围

这套账本与 RushWind CMS 的最小微服务账本同一哲学：每一行缺席都有替代物与加回条件，缺席是决策，不是烂尾。

九、机制 × 关键决策 × 失败模式

机制关键决策失败模式（若无此决策）
AES 信封 + 解密优先密文传输，服务端先解后验裸密码上路；或解密失败整个登录链瘫痪
client_type 分会话库双端同一登录面，凭据显式分流token 进错库，登录成功下一跳 401 循环
属性按本品组合收口radiogroup 只渲染组合内属性耳机页冒出尺码，规格区变成全局属性表
服务端定价事务客户端金额归零，价格行缺失即回滚零总额订单可创造可支付的对账洞
库存扣减 + 台账同行每笔扣减落 ORDER_DEDUCT争议无据可查，库存不可回放
意图 / 确认分离收银台两段式，迁移守卫拒重复成功幂等靠覆盖语义，重复支付静默通过
状态机单点迁移迁移表只在 core 一处旁路改字段，守卫沦为摆设
claim 强制注入「我的 XX」身份只来自凭据查询串点名任意用户，水平越权
缺席如实应答Unimplemented 进错误码假成功的壳混进生产路径

一笔订单穿过九道闸门，每一道的存在都能回答「没有它会坏什么」。这套答案的完整性，比任何功能清单都更接近「电商后端的生产就绪」——它意味着这条买路径不是演示动画，是一条有人对每一层签过字的路。
