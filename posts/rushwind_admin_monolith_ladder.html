RushWind Admin — 模块化单体：一个进程与通往微服务的五级阶梯

本文回答一个问题：一个 291 条路由、152 个 proto 文件、22 个顶层包的中后台，为什么整个后端只有一个进程？它和隔壁拆成三个进程的 RushWind CMS 是同一套框架底座——单体是妥协，还是另一种完成度？真到要拆的那天，单体里的每一件产物又去哪里？

RushWind Admin 是一套 Rust 中后台平台，后端是一个二进制。它的仓库文档没有为这个形态辩护，只标了一个坐标：一条五级演进阶梯的 L1，默认永远停在这里。而阶梯的另一端——L4 多服务——现成的参考实现，正是同底座的 RushWind CMS。

所以这篇文章不止回答「它为什么是单体」，还回答一个更少被问到的问题：一个单体离「能拆」有几步，每一步的触发器是什么，拆的时候单体里的每一件产物去哪里。

一、全部拓扑：一个进程，四条通道

先把「一个进程」说具体。拿到手的是一个二进制，监听一个地址（:7788），配置默认值嵌在二进制里（assets/ 下的 server.yaml、data.yaml、auth.yaml、oss.yaml 四份文档，环境变量覆盖生效）——部署它就是拷一个文件、给几个环境变量，没有容器编排清单，没有进程管理器配置。

进程里真正「听请求、干长活」的部件有四个。装配文档（server.yaml 头注释）管它们叫 transports，自我介绍：

# The server assembly document: one lifecycle, four transports. The
# factory transports — the SSE notification server and the task-queue
# worker — join the http edge as assembly-line transports. The tracing
# and profiling sections carry no transport here.
    bind: ":7788"

四条通道各管一段进出：

  • REST 边缘——所有 HTTP 请求的入口。注意它同时挂着两张 route pack（一包挂好的路由）：admin 面与业务模块面共用一台 HTTP 服务器、同一道 edge、同一层审计；
  • SSE 通知服务——事件从后端推向浏览器的那条线；
  • 任务队列 worker——后台任务（发邮件、跑报表这类）在这条通道里被领取执行；
  • cron 生产者——按时间表把定时任务放进同一条队列。

装配入口 main.rs 的文档注释把这台机器说全了：

// backend/apps/admin/src/main.rs
//! The application assembly entry: loads the embedded config defaults
//! (env overrides win), connects Postgres + Redis, builds the JWT
//! engines (RS256 verify + mint), runs the migration chains (admin
//! first — the module seeds address its tables — then each business
//! module's own chain) and the idempotent seeds, and hands the
//! transports — the REST edge (BOTH route packs: the admin surface and
//! the business modules ride one http server, one edge, one audit
//! layer), the SSE notification server, the task-queue worker, the
//! cron producer — to the config-driven lifecycle assembler (the
//! embedded server document, one `App`, one shutdown path).
//!
//! Adding a business module is four lines in this file: the migration
//! chain, the seed, the route pack — and the `mod` declaration beside
//! the others. Everything else about a module lives in
//! `src/modules/<name>/`.

这段注释里有几处值得停下来看的细节：

启动顺序是写死的依赖顺序。JWT 引擎先建、库先连，然后跑迁移链——admin 的迁移先跑，业务模块的随后。为什么？注释里给了理由：模块的种子数据要往 admin 建的表里插东西（角色、权限），admin 不先就位，模块种子就插不进去。单体里没有服务启动编排，依赖顺序由装配文件一锤定音。

基础设施不重复建设。任务队列只有一条，业务模块直接往里投 job：

// backend/apps/admin/src/main.rs
    // The shared task-queue storage handle: the worker (a factory
    // transport below) claims and executes; the periodic wildcard
    // pushes through. Business modules enqueue jobs on the same
    // queue instead of standing one up.
    let task_queue = Arc::new(apalis::TaskQueue::new(
        &state.cfg.database_source,
        "default",
    )?);

如果每个模块自己起一条队列，就是单体内的「微服务病」——每个域都想自带一套基础设施。这里从装配层就掐断了这种倾向。

对照隔壁：rushwind-cms 把「HTTP 边缘 + SSE」按消费端复制成两个 BFF 进程（BFF，站在前端身后、替前端裁剪后端的那一层），再把领域层单独关进一个不对外暴露的进程；admin 把同样四条通道压回一台机器——不是没想过拆，是还没轮到拆（触发器见第四节）。

二、模块化在哪：平台面、业务域与四行装配

「单体」两个字容易让人想到一团 .rs 意面——所有代码糊在一起，谁都能伸手到任何地方。这个仓的源码树先把两个世界分开了：

  • src/admin——平台面。身份、权限、审计这些平台域住在这里，连同它们各自离不了的横切件：审计写作、限流、分页、fieldmask（字段级裁剪）、验证码、加密、宏族（macros.rs）。你要往这个仓里找「中后台的通用能力」，就在这棵树里；
  • src/modules/<name>——业务域。每个业务域一个目录，services、data、migration、seed 各归各位。平台面是地基，业务域是租户——租户不碰地基。

这个分层形状与 rushwind-cms 的 core-service 内部结构同构。不是巧合，第五节的迁移地图会回收这一点。

模块的边界不是目录约定，是装配纪律——main.rs 里加一个业务模块真的只有四行：

// backend/apps/admin/src/main.rs
    if state.cfg.database_migrate {
        admin::migration::run(&state.db).await?;
        template::migration::run(&state.db).await?;      // ① 迁移链
    }
    admin::seed::run(&state).await?;
    template::seed::run(&state).await?;                   // ② 种子

    let mut assembler = Bootstrap::from_yaml_str(SERVER_YAML)?
        .route_pack("admin-surface", rest::pack(Arc::clone(&state)))
        // The business surface rides the same http server and edge —
        // one more line per module pack.
        .route_pack("business-surface", template::pack(Arc::clone(&state)));  // ③ route pack
    // ④ src/modules/template 的 mod 声明，与其余模块并列

四行里最值得琢磨的是 ③：业务模块的路由包挂在 business-surface 这个名字下，与 admin-surface 并列——但它搭的还是同一台 HTTP 服务器。模块多了以后，这台服务器就是所有域共用的门面；哪天某个域的流量大到要单独部署，它的 route pack 从这行摘下来、挂到新进程的 main 里，就是迁移的起点（第五节细说）。

仓里现存的业务模块只有 template 一个，它是「四行装配」教义的活样板：fork 它、改个路由前缀，就是一个新域——前缀怎么改，写在契约里（第五节实拍）。

域的规模感用数字说话，全部在一个进程内：契约树 152 个 proto 文件、602 条 RPC 声明，59 个 mount_service! 挂载的服务面，291 条 admin 路由 + 5 条 fork 路由。契约即文档，Swagger/ReDoc 直接从生成面出来：

单体不小，那纪律谁来盯？答案在 backend/testbed/ 里：一套差分台架对着 **296 条路由的 corpus（291 admin + 5 fork）**摆了 121 个 HEAD 探针 + 11 个精选用例，逐条验证路由的形状没有漂移，豁免项只有 3 类、每类写明理由；免鉴权白名单只有 8 个端点，在 auth_free.rs 与 tests/whitelist.rs 两处互相钉死，改一处不过另一处的测试就红。单体的健康不是口号，是有探针守着的。

三、默认停在 L1：五级阶梯，逐级触发

单体的完整说法藏在 docs/services-evolution.md 里——一条五级阶梯，每级有形态、有参照物、有触发信号：

级形态参照物触发信号
L1单应用 + src/modules 模块rushwind-admin 现状—（默认永远停在这里）
L2部署级 feature 门architecture-decisions §3.1不同部署要不同的域组合
L3lib 分发（三 crate 分层）architecture-decisions §3.3跨仓/跨团队的二开消费者
L4多服务（域出进程边界）rushwind-cms见第四节信号清单
L5规模化多服务成熟基础设施逐项进场多团队、多环境集群、严格合规

这条阶梯的骨架只有一句话：L4 之前的一切复杂度都是预支的——L2/L3 不改变进程拓扑，L4 才第一次引入进程边界；每一级只解决上一级解决不了的痛，不解决就不迈。

「预支」值得展开说。服务间契约、版本对齐、联调环境、部署编排——这些成本在 L1 本来一项都不存在，一旦拆了就项项常驻。在触发器响之前就背上它们，等于为一个还没发生的问题先行付息。

各级的现状如实摆一遍。L1 在跑，本文讲的就是它。L2/L3 已设计、未启用：Cargo.toml 里还没有一行 [features]——设计在文档里，纪律在触发器上，代码不动。但设计的形状值得一看，因为它决定了「拆」是扫地出门还是顺水推舟：

  • L2 的 feature 门是编译期开关：同一份代码，--features 的组合不同，编出来的部署件包含的域组合就不同。想给小客户出一个不带 AI 域的部署件？加一组 feature 就行，进程拓扑纹丝不动；
  • L3 的三 crate 分层改的是依赖方向：admin-contract（契约叶子，零依赖，只装类型与契约）/ admin-support（支撑件）/ 域 crates，依赖单向朝叶子收敛。这一层为什么是 L4 的直接前置？因为契约叶子在 L4 里就是域服务对外暴露的那份契约依赖——依赖方向不先掰正，拆出去的服务就带着一身反向依赖，剪不断。

L4 不是纸上架构：rushwind-cms 是已跑通的形态，五条形态规则（core 唯一领域层、契约双面、域服务不对外、前端零改动、同一套生成哲学）都有真实代码背书。L5 见第六节。

四、迈 L4 的门槛：触发信号 × 反信号

什么才算「轮到拆了」？阶梯文档给的是两组清单，全是硬条件。设计意图很清楚：拆不拆不看感觉，看清单。

触发信号（满足其一方才考虑）：

  • 独立伸缩曲线——某域的负载形态与整体显著偏离（读多写少、需要独立扩容与独立缓存层）；
  • 独立部署节奏——某域的发布频率远高于底座（底座冻结期域还要迭代，或反之）；
  • 非 Rust 消费方——域能力要被 Go/Python/移动端直连，gRPC 契约面成为刚需；
  • 独立数据版图——域需要独立的数据库实例、保留策略或合规边界；
  • 团队所有权——域归另一条产品线，发布权必须解耦。

反信号（出现这些时，留在 L1–L3）：

  • 「只想让代码分目录」——模块已经是；
  • 「只想按需部署」——L2 的 feature 门就是；
  • 「未来可能要多服务」——预支的多服务 = 把分布式复杂度搬进单体开发流（服务间契约、版本对齐、联调环境全是净增成本）；
  • 团队没有多服务的运维面——服务发现、链路、部署编排的持有成本是常驻的。

第三条反信号值得单独念一遍：「未来可能要多服务」本身被明文列为不拆的理由。「未来」不是一个时刻，是一组条件；条件没列进触发信号清单，「未来要拆」就只是焦虑，不是规划。这与直觉相反，却是这条阶梯的自洽逻辑。

五、接缝已预埋：拿 notice 这个域走一遍迁移地图

「默认停在 L1」不等于「拆的时候从零开始」。阶梯文档里有一张迁移地图：单体的每一件产物，在 L4 都有登记好的归宿。摘录主干：

单体内的产物L4 服务里的归宿
src/modules/<domain>/（services、data、migration、seed）services/core-service/ 的领域层
EdgePack route pack（server/edge.rs）拆两半：域方法 → core 的 gRPC server；对外整形 → BFF 的 REST 面
鉴权门（EdgePack 内 bind/门层序）上收到 BFF——门是网关职责；core 只做服务间身份
i_* BFF 投影面升维成整个 BFF 服务——单体里 i_* 是 admin 面的投影；多服务里 BFF 本身就是投影
独占的 PostgreSQL/Redis 连接core-service 独占（单体里模块与 admin 共库；拆出后数据版图随域走）

干看表格没感觉，拿现存的模板模块走一遍。它今天的样子：业务代码住在 src/modules/template/（services、data、migration、seed 四件套）；契约住在 api/fork/protos/notice/service/v1/；对外路由由一个 i_*.proto 投影面生成。这个投影面的自注释把身份写得明明白白——它就是单体里预埋的 BFF：

// backend/apps/admin/api/fork/protos/notice/service/v1/i_notice.proto
// 公告管理 BFF 服务——真正生成路由的那一个。路由前缀是模块独立前缀
// /template/v1/…（fork 时改成 /<你的模块>/v1/…），全部路由默认 gated
//（AUTH_FREE 为空表；要开放某端点，把它登记进 src/auth_free.rs 并在
// rpc 上补 gnostic security: {} 文档标注）。
service NoticeService {
  rpc List (pagination.PagingRequest) returns (notice.service.v1.ListNoticeResponse) {
    option (google.api.http) = {
      get: "/template/v1/notices"
    };
  }

拆的那天，沿着地图走：modules/template 的四件套整体搬进 core-service 当领域层；i_notice.proto 不再是投影面——它升维成整个 BFF 服务，路由生成逻辑原样跟过去；EdgePack 一拆为二，域方法变成 core 的 gRPC server，对外整形归 BFF 的 REST 面；鉴权门从 EdgePack 里搬出来，上收到 BFF——门是网关职责，core 只信内网里的服务间身份。

「升维」这个词不是修辞。对照 rushwind-cms 的结构：那边 admin-api/app-api 两个 BFF 的路由，全部由 passthrough_proxy! 生成的代理表承载；这边 59 个 i_* 面生成的路由直接挂在本进程的 edge 上。同一个动作（契约面投影成对外路由），单体里由投影面完成，多服务里由整个 BFF 进程完成——投影面本来就长着 BFF 的形状，所以迁移是「升级它」，不是「重造它」。

L3 的三 crate 分层是这条迁移路的最后一格台阶：admin-contract 契约叶子在 L4 就是域服务的契约依赖。阶梯文档的判断是：L3 做得越实，L4 的迁移越接近「把 route pack 挂到新 main」——前提是触发器响过、这一级真的被做过。

六、L5 的位置：与「最小微服务」篇对账

L5 的议题清单是：服务注册与发现（etcd/Consul）、OTel 链路追踪、跨服务一致性（Saga/分布式事务）、策略引擎外置（Casbin/OPA）。进场条件只有一条：多服务数量超过「一个人能口述全部拓扑」——超过之后，人脑管不过来的东西才交给基础设施管。

把同底座的两种拓扑对这批部件的态度摆在一起，正好接上「最小微服务」的缺席清单：

部件rushwind-cms（L4）的答案rushwind-admin（L1）的答案
服务发现 / 注册中心结构性替代：一条配置地址 + 共享 Channel不需要——进程内调用不存在「找服务」
消息总线结构性替代：metadata 带收件人 + 进程内 Hub不需要——同进程直接调用与事件
分布式事务结构性不存在：数据单主人，事务 = 进程内 DB 事务不存在——一个库一个事务边界
链路追踪 / OTel缺席：结构化错误信封 + E2E 裁决缺席：同一套门禁与 E2E 体系
策略引擎外置鉴权门内联（认证→租户→授权→注入）鉴权门内联，同一套宏与白名单

两种拓扑的差别不在「用了多少中间件」，在进程边界的数量：L1 零条，L4 两条（core 与两个 BFF 之间各一道）。中间件清单是进程边界的函数，不是架构品味的函数——边界画到哪，哪些部件从「不需要」变成「必需」，是被拓扑决定的，不是被潮流决定的。

七、机制 × 关键决策 × 失败模式

机制关键决策失败模式（若无此决策）
模块化单体平台面/业务域分树，一域一目录，四行装配域间耦合蔓延，拆分线无从画起
共享任务队列模块投 job 进同一条队列，不自建每域一套基础设施，单体里的微服务病
五级阶梯逐级触发，默认停在 L1预支的分布式复杂度搬进单体开发流
反信号清单「未来可能要多服务」列为不拆的理由按想象力拆服务，多出一份养不起的运维面
触发信号清单独立伸缩/部署/非 Rust 消费方/数据版图/团队所有权拍脑袋拆，拆完没有一条收益对得上信号
i_* 投影面59 个投影 proto 预埋 BFF 形状拆分时契约面重造，前端路由全断
迁移地图每件单体产物预登记 L4 归宿拆分变成考古，鉴权门与路由两处漂移
差分台架121 HEAD 探针 + 3 类豁免钉住 296 路由路由面静默漂移，拆分时对不上账
L2/L3 设计先行形状与代价写进文档，代码等触发器到用时才发现单体的分层根本接不上

单体是默认态，微服务是触发器驱动的例外。衡量一个单体是否健康，不看它有多小，看它离「能拆」有几步、每一步的触发器写没写下来——RushWind Admin 把这五步画在了文档里，路由面早就长着 BFF 的形状，但一步也不预走。
